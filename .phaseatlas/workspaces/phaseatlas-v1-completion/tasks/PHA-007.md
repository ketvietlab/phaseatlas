# Context

PhaseAtlas now has durable provider-neutral task execution, cancellation, replay, interruption, and
stale-result safeguards, but those capabilities stop at the repository worker and process manager.
The sandboxed renderer can inspect tasks and planning streams, yet it cannot determine permitted task
actions, start execution, reconstruct run history, review commands and results, or recover an
interrupted attempt without leaving the application.

This task delivers the typed desktop integration and an operational run workbench. Persisted checkout
state remains authoritative; the renderer is a resumable projection that merges live events with
cursor pages and never infers evidence authority from transient output.

# Requirements

- Define provider-neutral action-availability and run-summary contracts containing bounded task,
  revision, action, sandbox, provider/model, lifecycle, retry, freshness, and timestamp information.
- Evaluate actions inside the checkout worker against canonical validation, task write policy and
  state, blocking dependencies, abandoned attempts, registered provider capabilities, sandbox
  enforcement, and the provider-discovered model catalog. Return actionable blocking reasons.
- Expose explicit desktop/preload operations for action availability, run history, start, cancellation,
  cursor event pages, result review, and interrupted recovery. Do not expose generic worker RPC,
  Electron objects, commands, paths, process IDs, or provider payloads.
- Restore repository run history after reload and remember only the selected run as UI preference.
  Rebuild the transcript from persisted sequence zero, then resume strictly after the highest
  contiguous sequence.
- Merge pushed and fetched events by sequence, discard duplicates, detect gaps, and backfill them before
  advancing the cursor. Missed live events must not leave status, result, or activity permanently stale.
- Render repository history, task/revision identity, live lifecycle, normalized messages, command cards,
  command output, file changes, terminal outcomes, verification, blockers, Git-derived changed files,
  and current/stale/unverifiable result status.
- Require explicit acknowledgement of repository, provider/model, isolated worktree, sandbox, writable
  scope, and network policy before an implementation run starts.
- Make cancellation idempotent in the UI, show that PhaseAtlas is waiting for provider exit, and reload
  durable state afterward. Present interrupted attempts with bounded keep-history and linked-retry
  decisions.
- Keep result state advisory. A stale, unverifiable, interrupted, failed, or policy-violating result must
  never appear as current completion evidence.
- Meet keyboard, focus, contrast, responsive, dark-theme, and reduced-motion requirements using the
  KétViệt staff/operational design tokens.

# Implementation notes

- Add `AgentRunActionAvailability` and `AgentRunSummary` to shared contracts and a narrow `agentRuns`
  namespace to `PhaseAtlasDesktopApi`.
- Keep policy and history projection in the repository worker. Desktop main, process manager, and preload
  are typed routing layers only.
- Use one large operational review panel with a compact history rail and a detail surface for launch,
  timeline, and validated result review. Keep it independent from task Markdown and Monaco panels.
- Treat the operational store's sequence as the only continuity authority. Store selection preference in
  local UI storage, never run events or result authority.
- Group command lifecycle events by normalized `commandId`, but retain persisted event sequence for the
  surrounding timeline and replay logic.
- Render untrusted provider text as escaped Svelte text. Display repository-relative paths as labels and
  do not convert run worktree paths into arbitrary local file access.

# Constraints

- Reuse PHA-006 persistence, terminal compare-and-set, process ownership, event pages, result review, and
  recovery operations.
- Do not move policy evaluation, cancellation, result validation, freshness, or canonical authority into
  renderer memory.
- Do not auto-run write actions, auto-retry interruption, auto-promote evidence, or update canonical task
  state.
- Do not add dependencies, repository database migrations, provider credentials, external-network
  authority, generic shell access, or arbitrary filesystem/process APIs.

# Verification plan

- Query actions for writable/read-only tasks, incomplete dependencies, terminal task states, unavailable
  providers/models, missing capabilities, and abandoned attempts; verify clear fail-closed reasons.
- Start read-only and confirmed implementation runs through the typed bridge; verify immutable task
  revision, selected provider/model, derived sandbox, and isolated worktree behavior.
- Stream command, output, file, message, failure, cancellation, and terminal events; verify persist-before-
  display ordering and structured activity cards.
- Reload during an active run, replay from zero and an interior cursor, inject duplicate and out-of-order
  live events, and verify gap-free deduplicated reconstruction.
- Cancel responsive and non-responsive providers, race completion, and recover interruption; verify the UI
  reconciles one durable terminal outcome and creates only explicit linked retries.
- Change a task after a result and verify stale status and non-promotable review remain prominent.
- Complete keyboard-only, screen-reader status, light/dark, narrow-width, and reduced-motion review.
- Run `pnpm check`, `pnpm test`, and `pnpm build`, then request maintainer review of the typed boundary,
  action policy, continuity algorithm, confirmation gate, and result-authority presentation.
