# Context

PhaseAtlas already distinguishes configured repositories from legacy repositories in `packages/core/src/repository-inspector.ts`: a valid `.phaseatlas/repository.yaml` selects configured mode, while its absence selects legacy mode. Configured repositories discover workspaces and load canonical task YAML through `packages/core/src/task-loader.ts`. Legacy repositories currently have no workspace manifests, so inspection returns an empty canonical task snapshot and does not examine pre-PhaseAtlas task sources or report source-specific problems.

PHA-001 is the blocking dependency that defines the approved legacy formats, discovery rules, normalization, precedence, identity, provenance, and issue semantics. This task exists to turn that approved contract into deterministic shared types and core inspection behavior without weakening the existing authority of canonical `.phaseatlas/` manifests.

# Requirements

- Implement only the source formats and discovery paths explicitly approved by PHA-001. Each adapter must apply the contract's required-field extraction, normalization, defaults, precedence, size limits, and unsupported-input rules without heuristic parsing of unrelated repository documents.
- Represent normalized legacy candidates with the shared contract established by PHA-001, keeping them distinct from `CanonicalTask` and `TaskSnapshot.tasks`. Include the approved source-format discriminator, repository-relative provenance, source-native identifier or location, normalized fields, warnings, and deterministic candidate identity.
- Derive candidate identities exactly as specified by PHA-001. Identity and normalized candidate ordering must remain stable across repeated scans, different absolute checkout roots, filesystem enumeration order, and process restarts; timestamps and mutable runtime state must not participate.
- Apply the approved precedence and collision rules consistently across adapters. Identical duplicates, conflicting duplicates, missing native identifiers, and identity collisions must yield the contractually defined candidate or structured issue rather than depending on discovery or adapter registration order.
- Return stable, structured validation issues for missing, unreadable, malformed, oversized, partially valid, conflicting, or unsupported legacy inputs. Issues must include severity, code, actionable message, repository-relative source path, and an optional field or source location where available. A bad source must not crash repository inspection, and an ambiguous or invalid candidate must be excluded as required by the contract.
- Gate legacy ingestion on the repository classification already computed by `RepositoryInspector`. A repository with a valid PhaseAtlas repository manifest must continue to obtain tasks exclusively from canonical workspace and task manifests; legacy adapters must not run as a fallback or merge candidates into its canonical snapshot.
- Expose the legacy candidate-and-issue projection through the repository inspection boundary defined by PHA-001 while preserving `loadTaskSnapshot` as the canonical YAML projection and revision authority.
- Ensure `RepositoryInspector.invalidate()` clears any cached legacy projection so a subsequent inspection reflects changed source documents.
- Update the task contract documentation to describe the implemented adapter behavior and keep it aligned with the approved PHA-001 rules and shared TypeScript contracts.

# Implementation notes

- Add the approved candidate, provenance, source-format, and ingestion-result types to `packages/contracts/src/index.ts` before connecting them to core inspection. Reuse `ValidationIssue` where the approved contract permits it, but do not model a legacy candidate as either `CanonicalTask` or an already-approved `TaskProposal`.
- `packages/core/src/repository-inspector.ts` reads `.phaseatlas/repository.yaml`, assigns `RepositorySummary.configuration`, owns projection caches, and is the correct integration point for the configured-versus-legacy gate. Resolve and report source paths relative to the inspector's canonical checkout root.
- `packages/core/src/task-loader.ts` currently validates canonical task YAML, resolves canonical dependencies, constructs graph edges, and hashes canonical revisions. Keep `loadTaskSnapshot` canonical-only; do not feed adapter output into its parsed task collection or canonical revision calculation.
- Add adapter coverage to `packages/core/src/repository-inspector.test.ts`, following its temporary-Git-repository helpers. Under the current task scope, inline representative legacy inputs in temporary repositories; adding new fixture or adapter files requires an explicit scope update.
- Preserve the existing behavior in which malformed canonical task files become `ValidationIssue` entries without crashing the worker. Legacy parsing should follow the same fail-closed style while using the issue codes and candidate rules approved by PHA-001.
- Update `docs/contracts/task-contract.md` with the implemented source allowlist, authority gate, candidate projection, deterministic identity and ordering rules, precedence behavior, and structured failure semantics. Do not silently choose a format or policy that remains unresolved in PHA-001.

# Constraints

- Do not begin implementation until PHA-001 is approved and its required task state is `done`; this task must not invent missing formats, precedence, identity, or conflict policy.
- Do not parse arbitrary files, execute commands or embedded content from legacy sources, access paths outside the fixed repository root, follow unsafe traversal, or use external network access.
- Treat all legacy content as untrusted and non-authoritative. Adapters may produce candidates and issues only; promotion to canonical YAML remains a separate validated, explicitly reviewed action.
- Do not let a legacy candidate directly become a canonical task, alter canonical task state, satisfy dependencies, mark work complete, or participate in canonical revision hashes or graph edges before promotion.
- Do not fall back to legacy ingestion when a configured repository contains malformed workspace or task manifests. Existing configured-repository validation must continue to fail closed.
- Keep domain parsing in `packages/core`; do not move it into the Electron main process, add Node.js or Electron imports to the Svelte renderer, or broaden the preload API as part of this task.
- Stay within the canonical task's allowed paths. Do not add dependencies, database migrations, credential handling, network behavior, publishing UI, or automatic migration of legacy files.
