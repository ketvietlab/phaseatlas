# Context

PhaseAtlas currently keeps opened repositories and worker handles only in `RepositoryProcessManager` maps. `repositories.list()` therefore reports only live workers, and an Electron restart forgets every previously opened checkout. `RepositoryInspector.describe()` derives a stable repository ID from `.phaseatlas/repository.yaml` and a checkout ID from the canonical filesystem path, but the resulting catalog entry is not stored.

Planning and task-content runs also live entirely in worker memory. Their events have run-local sequence numbers, but events disappear on restart. A worker exit rejects pending requests, yet the manager retains no durable interruption state, has no explicit recovery transition, and can leave a dead handle associated with the checkout.

Workers currently stop only on explicit repository close or application quit. The documented lifecycle already defines cooling, idle shutdown, interruption, and recovery states, while ADR 0002 assigns a global catalog to the main process and a separate operational database to each checkout worker. This task establishes that persistence and supervision foundation before worktree leasing, execution providers, resume safeguards, and the history UI depend on it.

# Requirements

- Persist a global repository catalog under the operating system application-support location. Each entry must retain the canonical checkout path, checkout ID, repository ID, display metadata, and lifecycle/recovery metadata needed to reopen the checkout after the main process restarts.
- Preserve identity semantics across restarts: configured clones and worktrees may share the repository ID from `.phaseatlas/repository.yaml`, while each canonical filesystem path has its own checkout ID and isolated operational store. Reopening a catalog entry must validate the worker descriptor against the stored checkout identity and fail closed on a mismatch.
- Create one operational store per checkout under application-support storage. Only the worker bound to that canonical checkout may write the store; different checkouts must never share an operational database.
- Persist normalized run records and events transactionally before forwarding live events. Event sequence numbers must be unique and strictly increasing within a run, remain continuous after the store is reopened, and support reading the complete ordered stream without relying on in-memory deltas.
- Persist current planning and task-content lifecycle events through the same checkout-owned abstraction so their history survives worker or application restart. The abstraction must also be suitable for the normalized `AgentEvent` stream introduced by later execution tasks.
- On startup or recovery, identify persisted runs that were left non-terminal by a previous process. Record one durable interruption transition with the next sequence number; never infer completion or append duplicate interruption events on repeated recovery.
- Track worker demand separately from catalog membership. An open view and every active run must each keep the checkout worker alive. When both counts reach zero, start a configurable idle timer; cancel that timer if demand returns, and stop the worker only if both counts are still zero when the timer expires.
- Graceful idle shutdown must retain the catalog entry and checkout store. A subsequent request to reopen the checkout must create one replacement worker, even when multiple reopen or refresh requests arrive concurrently.
- Distinguish expected shutdown from unexpected exit. Unexpected exit must reject and clear every pending request, remove the dead handle from the live-worker registry, retain the catalog entry, and mark the checkout as requiring recovery.
- Make recovery explicit through the existing repository refresh/reopen flow or an equivalent manager operation. Recovery must coalesce concurrent attempts, start at most one replacement worker for the checkout, reopen its existing store, reconcile interrupted runs, and clear recovery-required state only after the replacement reports ready and its identity is validated.
- Persist only bounded operational metadata and normalized events. Do not persist provider credentials, authentication state, environment dumps, raw provider protocol payloads, canonical task manifests, policies, or authority to promote evidence or complete tasks.
- Update shared request, response, event, catalog, lifecycle, and persisted-run types in `packages/contracts/src/index.ts` before using them across worker or Electron IPC boundaries.

# Implementation notes

- `packages/contracts/src/index.ts` is the shared boundary for repository lifecycle state, recovery status, persisted run/event envelopes, and any worker messages needed to report run activity or recovery. Keep renderer-visible contracts provider-neutral and free of executable paths, credentials, and raw process handles.
- `packages/core/src/repository-inspector.ts` currently canonicalizes repository paths, reads the stable repository ID, and derives the checkout ID from a SHA-256 hash of the canonical path. Reuse those semantics when validating a catalog entry; do not create a second incompatible identity scheme.
- Add checkout-store implementation and focused storage tests under `packages/core/src`. Use the Node 24 platform SQLite capability or another already-available mechanism so this task does not require package dependency changes. Use explicit schema-version checks and transactional allocation of the next run sequence.
- `apps/desktop/src/main.ts` should resolve the application-support root through Electron, initialize the global catalog before serving repository IPC, and pass only validated storage locations to `RepositoryProcessManager`. Browser/view lifecycle should acquire and release checkout demand without moving repository parsing or run execution into the main process.
- `apps/desktop/src/repository-process-manager.ts` is the main-process supervisor and global-catalog owner. Replace process-local listing semantics with catalog-backed entries while retaining a separate live-worker registry. Model starting, online, cooling, interrupted, and recovery-required states; coalesce startup promises by checkout ID; distinguish requested stops from crashes; and make all manager calls reject cleanly when recovery is required or fails.
- `RepositoryWorkerHandle` already correlates requests and rejects pending calls on exit. Extend its exit notification so the manager can remove the exact dead generation without deleting a newer replacement worker. Readiness and exit handlers must be idempotent, including exits that occur before `worker.ready`.
- `apps/repository-worker/src/index.ts` is bound to `PHASEATLAS_REPO_ROOT` at process startup. Supply a checkout-specific operational database path through similarly constrained startup configuration, validate it before opening, and keep the database owned by that worker generation.
- Route `emitPlanningEvent` and `emitTaskContentEvent` through the durable event store. Persist first, then send IPC. Startup reconciliation should inspect non-terminal run rows and append interruption records before accepting recovery-sensitive work.
- Update `docs/architecture/repository-process-model.md` with the implemented demand-counting, idle, crash, and recovery transitions. Update `docs/decisions/0002-storage-boundaries.md` with concrete catalog/per-checkout locations, ownership, schema-version behavior, and the rule that operational data is not canonical authority.

# Constraints

- Keep all operational databases, events, logs, retries, and recovery markers outside the repository. This task must not add generated runtime files under `.phaseatlas/` or elsewhere in the checkout.
- The main process may own the global catalog and supervision state, but repository parsing and agent execution remain in the repository worker or core domain layer.
- Maintain exactly one live worker and one operational-database writer per canonical checkout. Never reuse a store across different checkout IDs or let an old worker generation affect its replacement.
- Keep the Svelte renderer free of Node.js, Electron, filesystem, and database imports. Desktop capabilities must continue to cross the typed preload/IPC boundary.
- Fail closed on invalid paths, identity conflicts, unsupported storage schema versions, or ambiguous/corrupt recovery state. Do not silently recreate a store in a way that loses event continuity.
- Do not persist credentials or copy provider-owned authentication state. Continue using the operating-system credential store or provider CLI authentication.
- Persisted run data is operational evidence only. It must not directly modify canonical task state, promote evidence, or mark a task complete.
- Do not add dependencies, external network access, repository database migrations, or a general migration capability. Internal application-support store initialization and explicit schema-version validation are limited to this persistence feature.
- Worktree leasing, execution scheduling, provider execution adapters, cancellation/resume semantics, stale-result promotion safeguards, renderer history UI, and release packaging belong to PHA-004 through PHA-008 and are non-goals here.

# Verification plan

- Add storage tests that create a temporary application-support root and configured repository, persist a catalog entry plus multiple events, close and recreate both stores, and assert that repository ID, checkout ID, canonical path, run metadata, payloads, and event order are unchanged.
- Verify transactional sequencing by appending events across a store reopen and asserting strictly increasing unique sequences. Include concurrent append attempts and repeated startup reconciliation to prove that exactly one interruption event is recorded.
- Open two canonical checkout paths for the same configured repository ID and verify that they receive different checkout IDs and database paths, cannot read each other's runs, and retain independent event sequences.
- Exercise idle lifecycle behavior with controlled timers or an injected clock: an open view prevents shutdown, an active run prevents shutdown after the view closes, returning demand cancels cooling, and the worker stops only after both demand counts remain zero for the full interval.
- Trigger concurrent reopen/refresh requests after idle shutdown and assert that the worker factory is invoked once, all callers resolve through the same ready worker, and the catalog entry and checkout store are reused.
- Fault-inject an unexpected worker exit while a request and run are active. Verify that pending requests reject, the dead generation is removed, the catalog records recovery-required state, normal calls do not spawn duplicate workers, and one explicit recovery starts one replacement and records a durable interruption.
- Verify an exit-before-ready and a repeated exit callback cannot leave a hanging readiness promise, delete a newer worker, or produce duplicate recovery records.
- Inspect temporary storage locations and database contents to confirm they reside beneath the supplied application-support root and contain no provider credentials, environment dumps, canonical task YAML, policy authority, or task-completion mutation.
- Run `pnpm check`, `pnpm test`, and `pnpm build` with the repository-pinned pnpm and Node.js 24.14.0 or newer.
- Request PhaseAtlas maintainer review of database ownership, identity validation, lifecycle state transitions, recovery behavior, and the updated architecture and storage-boundary documents.
