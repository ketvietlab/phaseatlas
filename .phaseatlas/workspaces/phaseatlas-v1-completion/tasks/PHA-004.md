# Context

`packages/contracts/src/index.ts` defines `AgentRunSpec` and normalized `AgentEvent` types, but they are currently declarations rather than an enforced execution boundary. A spec can contain raw `repositoryPath` and `worktreePath` values, while the repository-worker protocol has no implementation-run creation, scheduling, or lease operations. `apps/repository-worker/src/index.ts` runs planning and task-content agents from its startup-bound canonical repository root, but it has no general execution scheduler or worktree manager.

`RepositoryInspector` already canonicalizes the selected checkout, derives its checkout ID, validates canonical task YAML, and computes deterministic task revisions. Those values are not yet atomically captured into an immutable run specification. The existing result schema also permits a model to propose any task state, including `done`, without an implemented validation layer that preserves the proposal as advisory.

PHA-003 establishes checkout-owned operational persistence and recovery. This task builds on that ownership model so later provider adapters receive only validated execution context, concurrent implementation runs cannot collide, and interrupted lease state is visible instead of being silently recycled.

# Requirements

- Add a single backend run-creation path that accepts identifiers and execution intent, not caller-supplied filesystem paths or commands. It must resolve the task from the worker’s current `TaskSnapshot`, require an unambiguous valid canonical task, compare any expected task revision, and reject missing, invalid, stale, or checkout-mismatched requests before scheduling.
- Construct an immutable `AgentRunSpec` by snapshotting the canonical task revision, objective, optional body, source/context documents, scope, acceptance criteria, verification steps, requested action, sandbox policy, and the worker’s canonical repository and checkout identity. Runtime code must use this snapshot rather than rereading mutable task documents to assemble execution input.
- Derive sandbox policy in trusted code. Analysis, planning, and review actions must be read-only. A write-capable implementation action must require both a writable task scope and `workspace-write`; conflicting action, task-scope, or sandbox combinations must fail closed.
- Introduce a checkout-scoped worktree lease manager. Each `workspace-write` run must atomically acquire a lease owned by that run ID, create or validate one unique Git worktree derived from the worker’s canonical checkout, and receive its execution working directory only from the lease manager.
- Prevent simultaneous write runs from sharing a lease ID, worktree path, branch assignment, or working directory. Allocation must remain safe when requests start concurrently and must not rely only on checking whether a directory happens to exist.
- Run read-only actions from the fixed canonical checkout without acquiring a writable worktree lease. The execution handoff must enforce a read-only sandbox and refuse an adapter that cannot honor it; a subprocess must not be able to create, edit, or delete repository files or mutate Git index state.
- Bind every execution handoff to the validated directory selected by trusted scheduling code. Executors must not override the working directory, follow paths outside the canonical checkout or leased worktree, or receive authority for another checkout.
- Independently inspect Git changes for write runs instead of trusting `changedFiles` reported by the model. Normalize changed paths as repository-relative paths, reject traversal and `.git` targets, and identify changes outside the snapshotted allowed/forbidden scope as policy violations.
- Release normal leases in a guaranteed cleanup path after completion, failure, or cancellation. Cleanup may remove only the exact worktree registered to the lease after revalidating its checkout ownership; lease records and terminal disposition must remain auditable.
- On worker startup or lease-manager recovery, classify previously active leases as abandoned. Report their run ID, checkout identity, path, and recovery reason through the PHA-003 operational-state boundary. Do not automatically assign, delete, or silently reuse an abandoned worktree.
- Validate structured agent results against `packages/contracts/schemas/agent-run-result.schema.json` and shared TypeScript types before accepting them. Result paths and evidence references remain untrusted, and `proposedTaskState`—including `done`—must remain a recommendation requiring separate verification and promotion.
- Ensure no run-result or lease-completion path calls canonical task-writing APIs or directly changes a task’s state. Canonical `.phaseatlas/` task files must remain unchanged unless a separate authorized workflow performs that transition.

# Implementation notes

- Update `packages/contracts/src/index.ts` first with the run-creation input, immutable checkout/lease identity, worktree-lease lifecycle records, validated agent-result types, and worker request/event contracts needed by the scheduler. Avoid exposing arbitrary executable paths, working directories, credentials, or raw process handles across renderer-visible boundaries.
- Import and export `packages/contracts/schemas/agent-run-result.schema.json` through the contracts package, and keep its JSON Schema aligned with the TypeScript result contract. Preserve the explicit distinction between an execution outcome and an advisory proposed task state.
- `packages/core/src/repository-inspector.ts` and `packages/core/src/task-loader.ts` are the existing authorities for canonical roots, checkout IDs, task validation, normalized keys, and deterministic revisions. Reuse them when creating a spec instead of introducing another task parser or identity algorithm.
- Add focused execution-foundation modules under `packages/core/src` for run-spec construction/validation, result validation, Git change inspection, and worktree leasing, then export the supported surface from `packages/core/src/index.ts`. Use injectable Git/process and storage boundaries so concurrency, failures, and abandoned leases can be tested with temporary repositories.
- Integrate lease records with the checkout-owned operational storage established by PHA-003. Lease acquisition and ownership changes must be atomic with respect to competing requests, and runtime files must stay in application-support storage rather than `.phaseatlas/`.
- `apps/repository-worker/src/index.ts` is already permanently bound to `PHASEATLAS_REPO_ROOT`. Add scheduling there so requests are resolved against that worker’s inspector and checkout store, and so executors receive only the validated spec, sandbox, abort signal, and scheduler-selected working directory.
- Keep provider-specific command lines and output translation behind the runner boundary. PHA-005 will supply production execution adapters; this task should establish and test the provider-neutral scheduler/lease contract they must implement.
- Update `docs/contracts/agent-run-contract.md` with spec creation, sandbox derivation, result validation, advisory-state handling, and lease cleanup rules. Update `docs/architecture/repository-process-model.md` with lease ownership, concurrent allocation, abandonment detection, and recovery reporting.

# Constraints

- PHA-003 is a required predecessor. Do not recreate its global catalog, checkout operational store, worker recovery, or durable event-sequencing mechanisms.
- Keep repository parsing, scheduling, lease management, and agent execution out of the Electron main process. Keep the Svelte renderer free of Node.js and Electron imports.
- Never run a write-capable implementation agent in the canonical checkout. Read-only actions must not receive a writable lease or a fallback that weakens sandbox enforcement.
- Worktree cleanup must be narrowly scoped and recoverable. Do not recursively delete caller-provided paths, automatically prune ambiguous Git metadata, or remove abandoned worktrees before explicit recovery validation.
- Store no credentials, provider authentication state, raw environment dumps, or provider-specific payloads in run specifications or lease records.
- Do not add dependency changes, external network access, repository database migrations, or a general migration facility. Use the repository’s existing Node 24 and pnpm toolchain and the operational-storage abstraction supplied by PHA-003.
- Production Codex/second-provider execution adapters belong to PHA-005. Persisted resume, stale-result promotion, and full cancellation semantics beyond guaranteed lease cleanup belong to PHA-006. Execution-history UI and desktop workbench changes belong to PHA-007.
- An agent result is operational input only. It cannot promote evidence, bypass required human review, or mark a canonical task complete.

# Verification plan

- Add run-spec tests using temporary configured repositories. Assert that creation captures every required canonical field and checkout identity, that later task-file edits do not mutate the created spec, and that missing tasks, validation issues, stale expected revisions, unsafe paths, and checkout mismatches are rejected before scheduling.
- Add sandbox-policy tests covering every action, writable and non-writable task scopes, and conflicting requested sandbox values. Verify that only valid write-capable implementation runs can request `workspace-write`.
- Create a temporary Git repository and request several write leases concurrently. Assert that every run receives a distinct lease ID and worktree path, each worktree belongs to the expected canonical checkout, and no two active leases share a branch or working directory.
- Exercise the read-only execution boundary with a fixture command or fake adapter that attempts to create, modify, delete, and stage files. Assert that each mutation is denied and that the canonical checkout’s working tree, index, and HEAD remain unchanged.
- Exercise a write lease with an in-scope change and verify that Git-derived changed paths are reported relative to the leased worktree. Add traversal, `.git`, symlink-escape, forbidden-path, and out-of-scope cases and assert that they fail closed regardless of the model-reported `changedFiles` list.
- Cover success, thrown failure, and cancellation paths and assert that each releases its normal lease exactly once. Reopen the checkout store with an active lease record and verify it is reported as abandoned and excluded from subsequent allocation without silently deleting or reusing its worktree.
- Validate representative successful and malformed agent results against the shared schema. Include a result that proposes `done` and assert that the canonical task file, revision, and state remain unchanged.
- Run `pnpm check`, `pnpm test`, and `pnpm build` with pnpm 11.9.0 and Node.js 24.14.0 or newer.
- Request PhaseAtlas maintainer review of immutable-spec construction, checkout identity enforcement, sandbox fail-closed behavior, lease atomicity and cleanup, abandoned-lease recovery reporting, and the prohibition on direct task completion.
