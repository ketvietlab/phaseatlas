# Context

PhaseAtlas currently classifies a repository without `.phaseatlas/repository.yaml` as `legacy`, but task discovery only loads canonical YAML from `.phaseatlas/workspaces/<workspace>/tasks/*.yaml`. No contract defines which pre-PhaseAtlas documents may be inspected, how their contents become task candidates, or how conflicts and malformed input are reported. This gap blocks PHA-002 because adapter behavior cannot be implemented deterministically without an approved source, identity, precedence, and trust model.

# Requirements

- Produce an approval-ready legacy ingestion contract that enumerates every supported source format, its exact discovery path or glob, required structure, field extraction rules, defaults, and normalization behavior. Inputs outside this explicit allowlist must be unsupported.
- Define a legacy task candidate separately from `CanonicalTask`, including normalized candidate fields, source format, repository-relative provenance, source-native location or identifier, warnings, and deterministic candidate identity.
- Specify an identity algorithm that is stable across repeated scans and repository checkouts. It must not depend on absolute checkout paths, filesystem enumeration order, timestamps, or mutable runtime state.
- Define a total precedence order for all approved source formats and for multiple matching documents. State how identical duplicates, conflicting duplicates, missing identifiers, and collisions are handled; ambiguity must produce structured issues and exclude the affected candidate rather than selecting an arbitrary value.
- Preserve `.phaseatlas/` authority: when a valid PhaseAtlas repository manifest is present, canonical workspace and task YAML remain the only task source. Legacy-derived candidates must not be merged into `TaskSnapshot`, treated as canonical tasks, or published without existing validation and explicit human review.
- Define fail-closed behavior for missing, unreadable, malformed, oversized, unsupported, or partially valid sources. Failures must be represented with stable issue codes, severity, repository-relative source path, optional field or location, and actionable messages without crashing repository inspection.
- Include representative fixtures or worked examples for every supported format, plus cases covering precedence, stable identity, duplicate content, conflicting content, malformed input, unsupported input, and coexistence with configured PhaseAtlas files. Each example must show the expected candidates or issues.
- Record unresolved format or policy decisions explicitly; do not leave implementation to infer behavior from examples.

# Implementation notes

- Extend the source-authority and normalization rules in `docs/contracts/task-contract.md`; align the source-versus-projection and trust-boundary language in `docs/architecture/overview.md` if the approved contract introduces a new candidate projection.
- Use the existing `TaskProposal`, `CanonicalTask`, `ValidationIssue`, and `TaskSnapshot` definitions in `packages/contracts/src/index.ts` as boundary references. Any proposed legacy candidate or provenance shape must remain distinct from `CanonicalTask` and be suitable for shared runtime validation before IPC wiring.
- `packages/core/src/repository-inspector.ts` currently determines `RepositorySummary.configuration` from `.phaseatlas/repository.yaml`; the contract should identify this configured-versus-legacy decision as the ingestion gate.
- `packages/core/src/task-loader.ts` is the canonical YAML loader and revision authority. The future adapter implementation must not broaden this loader so that legacy documents silently become canonical tasks.
- Place representative implementation fixtures alongside the core adapter tests, following the temporary-repository style in `packages/core/src/repository-inspector.test.ts`, or document exact fixture inputs and expected normalized outputs if this read-only research task cannot add files.
- PHA-002 consumes this contract and is responsible for production adapters, validation, and automated tests. The contract should therefore be precise enough to implement without choosing additional precedence or identity rules.

# Constraints

- This canonical task is `research` with `scope.writable: false`; produce a reviewed contract/result only and do not modify repository files or implement adapters.
- Do not parse arbitrary repository documents, execute content found in legacy files, access paths outside the fixed repository root, follow unsafe path traversal, or use external network access.
- Do not treat legacy content as trusted, authoritative, or execution-ready. Promotion to canonical YAML remains a separate validated and human-approved action.
- Do not change canonical task state, dependency semantics, revision hashing, or completion authority as part of this task.
- Do not add fallback heuristics for unknown formats or resolve ambiguity by filesystem order, adapter registration order, or best-effort guessing.
- Keep domain parsing in `packages/core`; do not move it into the Electron main process or expose filesystem capabilities to the Svelte renderer.

# Verification plan

- Have a PhaseAtlas maintainer review the contract and confirm that every supported format has explicit discovery, parsing, normalization, precedence, identity, provenance, and rejection rules.
- Walk each representative fixture through the contract manually and compare the derived candidate fields, deterministic identity, ordering, and structured issues with the documented expected output.
- Repeat the identity examples with different absolute checkout roots and source enumeration orders; verify that candidate identities and normalized ordering remain unchanged.
- Review configured-repository and mixed-source examples to confirm that valid `.phaseatlas/` YAML is the sole authoritative task source and that legacy candidates never appear in `TaskSnapshot` without reviewed promotion.
- Review malformed, conflicting, unsupported, and unsafe-path examples to confirm that they fail closed with stable, source-located issues and no partially accepted ambiguous candidate.
- Confirm with the PHA-002 implementer or maintainer that the contract contains no unresolved implementation choices and can be translated into shared types, core adapters, and automated fixtures without weakening existing trust boundaries.
