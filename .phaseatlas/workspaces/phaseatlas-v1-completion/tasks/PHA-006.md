# Context

PhaseAtlas can now dispatch provider-neutral task runs, but durable execution still needs explicit
rules for cancellation, application restart, event replay, and task changes that occur while an agent
is working. Without those rules a renderer can appear frozen, a provider can continue writing after
the user cancels, or an obsolete result can be mistaken for current evidence.

This task makes the checkout operational store the source of truth for run lifecycle and results. It
also defines recovery as a new linked attempt rather than pretending that an interrupted provider
process can be resumed in place.

# Requirements

- Persist the immutable run specification, normalized events, structured result, retry linkage, and
  result revalidation records in checkout-owned application-support storage.
- Assign every event a durable monotonic sequence before publishing it live. Support bounded cursor
  pages so a reconnecting consumer can resume strictly after its last contiguous sequence.
- Terminalize a run through one atomic compare-and-set transition. Repeated cancellation, natural
  completion, adapter failure, and process-exit races must yield exactly one terminal state.
- On accepted cancellation, signal the owned provider process group, wait for confirmed exit, and use
  bounded force termination when graceful termination is ignored. Do not accept output after abort.
- Release the exact worktree lease only after provider termination and terminal persistence. Preserve
  ambiguous worktrees as abandoned for explicit recovery.
- Mark active runs interrupted after worker restart. Expose an explicit decision to leave the run
  interrupted or create a new linked retry from a freshly validated canonical task.
- Persist validated results before the terminal event becomes observable. Duplicate or late results
  fail closed.
- Compare every result's task revision with the current canonical revision before promotion. A stale
  result remains non-promotable until a trusted revalidation records the exact current revision, and
  becomes stale again after any later task revision.
- Keep renderer and desktop operations typed and bounded. Do not expose arbitrary commands, process
  identifiers, executable paths, worktree paths, environment data, or provider-specific payloads.

# Implementation notes

- Extend the checkout operational store with append-only run specifications, results, retry links,
  revalidation records, cursor pages, and an atomic terminal transition.
- Keep audit events after terminal state limited to recognized lease and result-revalidation prefixes;
  reject late provider output and lifecycle mutations.
- Split scheduler preparation from execution so a run is durably visible before asynchronous provider
  execution begins.
- Own active abort controllers inside the checkout-bound repository worker. Desktop process management
  forwards sanitized events and ignores obsolete worker generations.
- Treat recovery as a new run identifier whose specification is rebuilt from the current task snapshot;
  retain the prior interrupted run and linkage for audit.
- Centralize freshness review in core code so renderer state cannot declare a stale result promotable.

# Constraints

- Reuse the checkout identity, worktree lease, runner registry, result validator, and normalized event
  contracts established by earlier tasks.
- Do not mutate canonical task YAML, promote evidence, infer completion, or automatically retry an
  interrupted run.
- Do not add a generic process manager, shell API, unrestricted filesystem API, dependency changes,
  repository database migration, or external-network authority.
- Persist no credentials, environment dumps, executable locations, raw process handles, or opaque
  provider payloads.

# Verification plan

- Race repeated cancellation with natural completion and adapter failure; verify one terminal event,
  confirmed provider exit, no post-terminal output, and one lease disposition.
- Run a fake child that ignores graceful termination; verify bounded force termination and that the
  cancellation response waits for process close.
- Persist events, reopen the operational store, and page from zero, an interior sequence, and the tail;
  verify gap-free, duplicate-free ordering.
- Restart with an active run; verify it becomes interrupted and only an explicit recovery choice can
  create a separately identified, linked retry.
- Record a result, change its canonical task, revalidate it, and change the task again; verify the
  freshness sequence is current, stale, current, then stale and promotion is denied whenever stale.
- Submit malformed cursors, forged identifiers, duplicate results, late output, and unsupported recovery
  decisions; verify fail-closed behavior.
- Run `pnpm check`, `pnpm test`, and `pnpm build`, then request maintainer review of process ownership,
  terminal ordering, cursor semantics, recovery, and stale-result authority.
